# Phase 4 — OpenACC GPU 백엔드 (`openacc`)

노드 `gpgpu` · NVHPC 25.11 (사용자 홈 설치) · RTX 5090 (cc120) · CUDA 13.0 번들 · fp64
빌드: `make -C libs/fortran acc` → `libs/fortran/build/cfd_exp_acc`

---

## 1. 포팅 방식 — 소스 하나, 플래그로 백엔드 선택

`!$omp` 와 `!$acc` 를 **같은 소스에 병기**했다. `-mp` 로 컴파일하면 `!$acc` 줄이 주석이 되고,
`-acc` 로 컴파일하면 `!$omp` 줄이 주석이 된다. 문헌 L7이 OpenACC의 장점으로 드는
"소스 변경 최소화 + 가속기 플래그 없이도 CPU에서 그대로 동작"이 그대로 성립한다.

```fortran
!$omp do collapse(2) schedule(static)
!$acc parallel loop collapse(2) gang vector
do j = 1, ny
   do i = 1, nx
      ...
   end do
end do
!$acc end parallel loop
!$omp end do
```

- 오프로드된 루프 **21개** (operators 5, solvers 8, schemes 8)
- **추가 코드량 42줄** (지시문 21쌍). 계산 코드는 **한 줄도 바뀌지 않았다.**
- 메모리: `-gpu=mem:managed` (통합 메모리) → **데이터 이동 절 없음.**
  NVIDIA가 NEMO GYRE_PISCES 포팅에서 쓴 방식과 같다 (L7).

## 2. R2 게이트 — 통과

| 케이스 | 검사 | rel L2 (η) | rel L2 (u,v) | 허용오차 | 판정 |
|---|---|---:|---:|---:|---|
| `igw` | 1 step | 1.011e-16 | 1.114e-16 | 1e-12 | **PASS** |
| `igw` | full run (56) | 3.340e-14 | 2.163e-14 | 1e-9 | **PASS** |
| `geo_balance` | 1 step | 4.515e-16 | 1.315e-15 | 1e-12 | **PASS** |
| `geo_balance` | full run (1549) | 9.322e-12 | 1.295e-11 | 1e-9 | **PASS** |

### 2.1 게이트가 잡아낸 버그 — 기록해 둘 가치가 있음

첫 빌드는 **`rel L2(η) = 정확히 1.000`** 으로 실패했다. η가 전부 0이라는 뜻이다.

원인: 리덕션용 모듈 스칼라에 `!$acc declare create(red_a, red_b, red_c)` 를 붙인 것.
**OpenACC의 `reduction` 절은 결과를 호스트 변수로 직접 복사해 준다.** 그런데 미리
`declare create` 로 디바이스 상주 사본을 만들어 두면 호스트는 **낡은 값(0)** 을 계속 읽는다.
그 결과 `norm_b = 0` → PCG가 즉시 반환 → `x = 0` → η = 0.

> **이 버그는 조용하다.** 컴파일 경고도, 런타임 오류도, GPU 오류도 없다.
> 결과 그림만 보면 "뭔가 이상하다" 정도로 넘어갈 수 있다.
> **수렴차수도 아니고 눈대중도 아닌, `ref` 대조 수치 게이트(R2)만이 이걸 잡는다.**
> 이것이 RULES.md R4("검증 없는 성능 수치 금지")가 존재하는 이유다.

`declare create` 를 제거하고 리덕션 절이 스스로 처리하게 두는 것이 정답이다.

## 3. **RQ5에 대한 답 — CPU↔GPU 손익분기 격자크기**

동일 노드(`gpgpu`) 안에서 측정 — CPU는 Threadripper 9955WX, GPU는 RTX 5090.
`igw`, CFL 0.5, `n_steps ∝ nx` (dt ∝ dx 이므로 총 작업량은 `nx³` 로 증가), 3회 반복 median.

| nx | 수평 격자점 | CPU 1스레드 [s] | CPU 16스레드 [s] | **GPU (OpenACC) [s]** | GPU / CPU-16t |
|---:|---:|---:|---:|---:|---:|
| 64 | 4,096 | 0.0140 | 0.00483 | 0.0532 | **0.09×** (GPU 11배 느림) |
| 128 | 16,384 | 0.1192 | 0.0171 | 0.1185 | **0.14×** (7배 느림) |
| 256 | 65,536 | 1.0390 | 0.1197 | 0.2826 | **0.42×** (2.4배 느림) |
| 512 | 262,144 | 8.7667 | 0.8937 | **0.6443** | **1.39×** ← 역전 |
| 1024 | 1,048,576 | 73.208 | 11.068 | **1.8908** | **5.85×** |

**손익분기는 nx ≈ 400, 수평 격자점 약 1.6×10⁵ 지점이다.**

### 3.1 이 프로젝트의 목표 격자에 대한 의미

> **목표 격자 100×100 = 10,000 점은 손익분기보다 16배 아래다.**
> 이 크기에서 GPU는 CPU보다 **약 9배 느리다.**
> 이는 하드웨어나 포팅 품질의 문제가 아니라 **문제가 너무 작다**는 사실의 측정이다.
> 커널 실행 지연(스텝당 21회 launch × 5~10 µs)이 계산 시간을 완전히 지배한다.

설계문서 위험요소 **T1** 이 이로써 정량적으로 확정되었다.
**단일 격자 크기에서 나온 GPU 비교는 이 프로젝트에서 무효다.**

### 3.2 중요한 단서 — 3D에서는 달라질 수 있다

위 손익분기는 **2D 순압 문제의 수평 격자점 수** 기준이다.
Phase 2의 3D(100×100×30)에서는 셀 수가 3×10⁵ 로 **손익분기 근처까지 올라오고**,
연직 방향 작업(배치 삼중대각 10,000개 × 크기 30)은 커널당 병렬도를 크게 키운다.
**따라서 "100×100 격자에서는 GPU가 무의미하다"고 일반화하면 안 된다** —
3D에서 다시 측정해야 한다. 이것이 Phase 2를 건너뛸 수 없는 이유다.

## 4. 아직 하지 않은 것

| # | 항목 | 왜 필요한가 |
|---|---|---|
| 1 | `mem:separate` + 명시적 `!$acc data` 리전과 비교 | managed memory의 페이지 마이그레이션 비용을 분리. L7의 "포팅 노력 vs 성능" 교환을 정량화 |
| 2 | 커널 융합 (21개 → 더 적게) | 스텝당 launch 횟수가 작은 격자를 지배. 손익분기를 왼쪽으로 옮길 수 있다 |
| 3 | Nsight Compute roofline | 실제 AI 를 손계산이 아니라 측정으로 (docs/12 §4) |
| 4 | CUDA Fortran / CUDA C 백엔드 (P5) | OpenACC 대비 튜닝 여력 비교 (RQ3) |
| 5 | 광대역 우변 케이스 | 현재 PCG가 1~2회로 수렴해 **전역 reduction 비용이 거의 안 잡힌다.** RQ2의 전제조건 |
| 6 | fp32 / mixed 변형 | docs/12 기준 예상 이득 약 2배 (48배가 아님) |

> ⚠️ **§3의 수치는 잠정이다.** 항목 5 때문에 semi-음해법의 타원형 해 비용이
> 실제보다 훨씬 싸게 잡혀 있고, 그 부분이 GPU에서 가장 불리한 부분이다.
> 즉 **현재 측정은 GPU에 유리한 쪽으로 편향되어 있다.**
