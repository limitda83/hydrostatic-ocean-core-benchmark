# 32. 하드웨어 사다리 — 바이트 동일한 50 스텝을 세 장치 · 다섯 구현으로

**날짜:** 2026-09-15 (2026-09-13 초판을 `tools/audit_crossdevice.py` 감사로 정정;
같은 날 **H100 OpenACC 열 전체를 R4 게이트를 통과한 이진으로 재측정**해 갱신 — docs/90 **N42**)
**실험:** `expr/E13_tier2_ladder` (조각 H) + `expr/E14_v06_representative`
**문제:** 같은 케이스·같은 격자·같은 dt 로 **정확히 50 스텝**. 백엔드마다 문제 파일이 바이트
동일하고, θ 계열은 **솔버 반복수가 자리까지 일치**해야 행이 유효하다.
**노드(R7-1 역할):** `ktcloud` H100 (GPU 전용) · `gpgpu` RTX 5090 + Threadripper PRO 9955WX
16C (같은 노드 CPU↔GPU) · `geo85` EPYC 9655 96C/192T (PBS 배타, CPU 확장성 전용)
**보고:** 스텝당 ms, 5회 median, 괄호는 **MAD/median**. CPU 는 격자별 최적 스레드 수를 병기.

> **한 표 = 한 문제.** 표마다 케이스·스킴·솔버·CFL·스텝수가 하나로 고정된다. 이 규칙은 이제
> 사람이 지키는 것이 아니라 `tools/audit_crossdevice.py` 가 이 문서의 모든 칸을 보존 데이터에
> 되짚어 검사한다 — 한 칸이라도 다른 CFL·다른 솔버·발산한 실행에서 왔으면 감사가 실패한다.
> 초판의 §2 가 정확히 그렇게 세 출처가 섞인 표였다(docs/90 **N39**).

> **굵은 값은 MAD > 2 % 다.** 그 행은 단일 수치로 인용하지 않는다 — 이 벤치마크에서 큰 분산은
> 두 가지 서로 다른 원인을 갖는다: `ktcloud` 는 타 테넌트 경합(docs/90 **N26**), `gpgpu`·`geo85`
> 의 다중스레드는 **투명 거대페이지 폴백에 의한 이봉분포**(docs/90 **N29**)다. 후자는 빈 노드에서도
> 재현되며 스레드 고정으로 사라지지 않는다.

## 2-2. 2000² 의 θ 는 CFL 4 에서 발산한다 (R12) — 수렴하는 설정은 CFL 2 뿐

2000²×30 에서 θ=0.5 는 **CFL 4 에서 두 솔버 모두 max_iter(스텝당 2000회)에 걸린다** —
다중격자 121128 its/50 스텝, PCG-Jacobi 121956 its/50 스텝. 즉 그 격자의 CFL 4 행은 시간이

## 4. 사다리가 말하는 것

1. **장치 순위는 격자에 따라 뒤집힌다.** 100² fb 에서 H100 CUDA 0.64 ms 는 **다른 노드의**
   EPYC 9655 64스레드 3.18 ms 보다 5.0배 빠르다(두 장치를 비교하는 것이므로 R7 허용, 다만
   두 장치명을 함께 적는다). 같은 문제에서 RTX 5090 CUDA 1.14 ms 는 그 EPYC 보다 2.8배 빠를
   뿐이고, **같은 노드의** Threadripper 16스레드(6.38 ms)와 비교하면 5.6배다.
   **어느 CPU 를 기준선으로 쓰느냐가 배율을 두 배 이상 바꾼다** — R8-1 이 두 기준선을 요구하는
   이유다. 같은 노드 비교만이 RQ2/RQ3/RQ5 의 1차 수치가 된다.
2. **2000² 는 용량이 순위를 정한다.** RTX 5090(32 GB)에서 CUDA·JAX 는 OOM 이고, 관리메모리를
   쓰는 OpenACC 만 3941.66 ms/스텝으로 돌아 **같은 노드 CPU 16스레드(4284.10)와 사실상 같다.**
   H100(80 GB)은 같은 문제를 166.47 ms 로 푼다 — **23.7배**. 연산성능이 아니라 메모리 용량의
   함수다(docs/90 **N24**). θ 계열(§2-2)에서는 그 결과가 **순위 역전**까지 간다: EPYC 9655
   192스레드 566.19 ms 가 RTX 5090 OpenACC 4279.07 ms 보다 **7.6배 빠르다.** 이 벤치마크에서
   "CPU 가 GPU 를 이긴다"가 가장 크게 나오는 자리이며, 원인은 CPU 의 강함이 아니라 32 GB 카드의
   관리메모리 왕복이다.
3. **작은 격자에서 GPU 는 같은 노드 CPU 에 진다.** 100² θ·mg 에서 RTX 5090 OpenACC 48.49 ms 는
   같은 노드 CPU 16스레드 11.99 ms 보다 **4.0배 느리고**, CUDA 조차 9.27 ms 로 **1.29배**에
   그친다. 커널 발사가 지배하기 때문이다(docs/35: 100² 에서 다중격자 평활자가 스텝당 705회 발사).
   솔버를 PCG-Jacobi 로 바꾸면 같은 격자에서 OpenACC 19.95 ms 대 CPU 9.52 ms 로 벌금이 절반이
   된다 — **발사 횟수가 적은 솔버일수록 작은 격자에서 GPU 가 덜 손해다.**
4. **구현 간 격차가 장치 간 격차보다 작아지는 지점이 있다.** 1000² fb 에서 RTX 5090 의 세 GPU
   구현은 57.80(JAX) · 66.24(CUDA) · 71.97(OpenACC) ms 로 1.24배 안에 모이지만, 같은 문제의
   H100 대 5090 은 29.02 대 66.24 = 2.28배다. 큰 격자에서는 **어느 프레임워크로 쓰느냐보다
   어느 카드에 올리느냐가 크다.** 작은 격자에서는 반대다 — 100² θ·mg 에서 5090 위의 구현 간
   격차는 6.13(JAX) 대 48.49(OpenACC) = **7.9배**인데 장치 간 격차는 CUDA 기준 7.16 대 9.27
   = **1.29배**뿐이다.
5. **물리를 켜면 사다리가 눌린다.** §3 을 §1 과 비교하면 v0.6 에서 모든 칸이 느려지되 그 비율이
   장치마다 다르다 — 셀당 분해는 docs/31, 그 원인은 docs/34·36 이다.

## 5. 규칙 준수

- R7-1: `ktcloud` 의 CPU 시간은 어느 표에도 없다. CPU 열은 `gpgpu`(같은 노드 비교용)와
  `geo85`(확장성 전용) 두 줄뿐이다. `tools/audit_crossdevice.py` 의 검사 C4 가 이를 강제한다.
- R7-2: 5회 median + MAD. MAD 를 모든 칸에 병기했고 2 % 초과는 굵게 표시했다(검사 C5).
- R5: 한 표 안에서 바뀌는 축은 격자와 백엔드뿐이다. 케이스·스킴·솔버·CFL·dt 는 표마다 고정이며
  검사 C2 가 모든 칸의 출처가 하나임을 확인한다.
- R8-1: 이 문서는 배율을 §4 에서만 쓰고, 쓸 때마다 두 장치와 스레드 수를 같은 문장에 적는다.
- R12: 발산한 실행은 시간으로 보고하지 않는다(§2-2). 검사 C3 가 이를 강제한다.

## 6. 한계와 남은 측정

- **완료된 재측정이 이 표에 반영되어 있다.** `geo85` 의 96/192스레드와 직렬, `ktcloud` JAX 의
  100²·200² 는 2026-09-14 재측정본(`geo85_r2.csv`, `ktcloud_jax_stab.csv`)이다. 초판은 이
  재측정이 케이스 토큰에 `.r2`/`.stab` 꼬리표를 달았다는 이유로 **오염이 확인된 구판 값을 계속
  싣고 있었다**(docs/90 **N39**). v0.6 1000² EPYC 는 488.32 → 390.74 ms 로 20 % 바뀌었다.
- 남은 MAD > 2 % 는 두 칸이다: §1 100² RTX 5090 OpenMP(2.2 %), §1 400² EPYC OpenMP(3.9 %).
